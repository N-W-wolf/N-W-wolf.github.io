AI 工具正在逐渐成为软件开发中的常用工具。对于机器人开发来说，它的价值不只体现在代码补全或回答问题，还可以参与代码阅读、方案分析、调试排查、文档整理、测试验证等工作。

但 AI 并不会因为接触到一个项目，就自动理解项目的结构、硬件条件和开发目标。尤其在机器人系统中，软件往往与电机、传感器、通信链路和真实机械结构紧密相关。如果缺少必要的上下文，即使生成的代码能够编译，也可能并不符合实际系统的需求。

因此，本章的重点不是介绍某一种具体 AI 产品，而是学习怎样把 AI 和 Agent 正确地纳入工程开发流程。

## AI 与 Agent 的基本区别

日常使用的对话式 AI 通常以“提问—回答”为主要交互方式。它适合解释概念、分析问题、讨论方案、阅读代码或整理资料。

Agent 则进一步具备了操作工具和工作环境的能力。一个 Coding Agent 通常可以直接读取项目文件、搜索代码、修改文件、运行终端命令，并根据编译结果或测试结果继续调整。例如，当我们让普通对话式 AI 分析一个程序时，通常需要手动把相关代码提供给它；而 Agent 可以进入代码仓库，自行查找程序入口、阅读相关模块，并直接完成修改和验证。

这使 Agent 更适合处理真实工程任务，但也意味着它能够产生更直接的影响。文件修改、依赖安装、Git 操作甚至硬件相关代码都可能由 Agent 执行，因此使用方式需要比普通聊天更加谨慎。

## AI 在机器人开发中的作用

机器人项目通常包含较多模块，而且涉及软件与真实硬件之间的交互。一个成员可能需要同时面对 Linux、C/C++、Python、ROS 2、通信协议、控制程序、强化学习训练和各种第三方库。

在这种情况下，AI 很适合作为辅助工具参与开发。例如，它可以帮助快速理解陌生代码，解释某个接口的调用关系，根据日志整理可能的故障原因，查找实现某个功能涉及的文件，或者协助完成重复性的代码和文档工作。

对于第一次接触某项技术的成员，AI 也可以降低查阅资料的门槛。遇到一个新的概念时，可以先通过对话建立基本认识，再继续阅读官方文档和源码；遇到报错时，也可以让 AI 根据日志和环境信息协助确定下一步应该检查什么。

但 AI 输出本身不能代替验证。机器人程序最终运行在真实系统上。一个看起来合理的修改，仍然可能因为接口理解错误、时序问题、单位错误或硬件条件不同而产生问题。因此，AI 更适合参与“分析和实现”，而最终结果仍需要通过代码检查、编译、测试、仿真和实机实验确认。

## 从“使用 AI”到“与 Agent 协作”

简单使用 AI 并不困难。真正需要学习的是如何让它稳定地参与一个持续开发的工程。例如，对于“机器人偶尔出现通信超时”这样的问题，直接要求 Agent“修复通信问题”通常不是一个好的任务定义。Agent 并不知道通信拓扑、运行周期、最近做过哪些修改，也无法确定超时究竟来自驱动、电机、线程调度还是上层程序。

更合适的方式是先明确现象和约束，让 Agent 阅读相关代码和日志，理解当前实现，再提出可能原因和验证方案。确认分析方向后，再进行修改，并通过测试结果判断问题是否真正得到解决。

因此，一个比较完整的协作过程通常包括：**明确任务 → 提供上下文 → 阅读工程 → 分析问题 → 制定方案 → 修改实现 → 执行验证 → 检查结果**

后续章节会围绕这一流程逐步展开。

## 使用 AI 的基本原则

我们不应该把所有工作交给 AI，也不应该以“尽量不用 AI”作为目标。更合适的原则是：**可以充分使用，但必须理解输入、检查过程并验证结果。**

当 AI 能够帮助快速阅读一个陌生模块时，没有必要坚持逐行从头分析；当 Agent 能够自动完成一次机械性的接口修改时，也没有必要手动重复劳动。但对于关键控制逻辑、系统架构、安全相关代码以及真实机器人测试，开发者仍然需要知道发生了什么，并能够判断结果是否合理。AI 和 Agent 最适合承担的是开发过程中的辅助工作，而最终对机器人行为负责的仍然是开发者。
