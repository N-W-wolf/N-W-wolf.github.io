## 1. 从模型到 AI 工具 

目前来说，以 LLM 为核心的 AI 应用已经逐渐划分为两个层次：一是负责处理信息和生成结果的人工智能模型，二是建立在模型之上的具体应用和工具。当下我们接触到的 AI 工具，已经是一套由模型、界面、文件系统、搜索能力、代码执行环境和其他工具共同组成的产品。

### 1.1 大语言模型

近年来常见的生成式 AI，大多以**大语言模型（Large Language Model，LLM）**为基础。

从使用者的角度，可以先把大语言模型理解为一种能够根据输入内容生成后续内容的模型。输入可以是一段问题、代码、文档或其他信息，模型根据已有上下文生成相应的回答。例如，输入一段 C++ 报错信息并询问原因，模型可以分析错误信息并给出可能的解释；输入一个函数和修改要求，模型可以生成修改后的代码；输入一篇论文，也可以根据文章内容进行概括和解释。

现代模型的能力已经不再局限于普通自然语言。一些模型能够较好地处理：

- 程序代码；
- 数学表达式；
- 表格和结构化数据；
- 图片；
- 文档；
- 音频等其他信息。

能够同时处理文本、图像等多种信息形式的模型，通常称为**多模态模型（Multimodal Model）**。

需要注意的是，模型并不是一个能够随时访问所有信息的“知识库”。模型在生成结果时，一部分能力来自训练过程中获得的知识和模式，另一部分则来自当前提供给它的上下文。如果问题涉及一个模型从未看到过的项目代码、最新的软件版本或者团队内部设计，仅仅依靠模型自身通常不足以得到可靠结果。

此外，在讨论具体 AI 产品时，还需要注意“模型名称”和“产品名称”之间的区别。例如，一个模型系列可能被不同的软件产品调用，而同一个 AI 产品也可能在不同时间提供多个模型供用户选择。因此，在比较 AI 工具时，需要分别关注：**使用了什么模型，以及这个产品围绕模型提供了什么能力。**

### 1.2 AI 应用与服务

普通用户真正接触到的 AI，通常是一套建立在模型之上的应用，而不是模型本身。一个完整的 AI 应用除了调用模型，还可能负责保存和组织对话、读取上传的文件、搜索互联网、执行代码等等。因此，即使两个工具使用的底层模型能力接近，它们在实际工程开发中的表现也可能存在明显差异。

例如，对于一个机器人项目中的代码问题，如果工具只能进行文字对话，就需要由开发者手动复制代码和报错信息。而另一种工具可能能够直接访问项目目录，搜索相关函数、读取多个源文件、执行编译命令并查看结果。

后者在处理完整工程任务时通常更加方便。这种区别并不只是来自“模型更强”，还来自工具是否能够获得项目上下文，以及是否具有相应的操作能力。所以，在后续选择 AI 工具时，不应只比较某个模型在排行榜中的成绩，还需要考虑实际使用环境，比如能否稳定访问，是否支持文件和图片等，这些因素往往更加影响实际体验。

总的来说，模型提供基础的理解和生成能力，AI 应用负责把模型与真实任务所需要的信息、工具和工作环境连接起来。在此基础上，如果系统进一步允许模型连续使用工具、观察执行结果，并根据结果决定下一步操作，就开始进入后面要介绍的 **Agent** 范畴。

## 2. 大语言模型的基本交互机制

要更好地使用大语言模型，首先需要理解：模型并不是在读取整个数据库后回答问题，而是在当前能够获得的信息范围内生成结果。对于使用者来说，最需要了解的几个概念是 **Token、上下文（Context）和上下文窗口（Context Window）**。它们直接影响模型能够看到多少信息，以及我们应该怎样向模型提供代码、文档和任务描述。

### 2.1 输入、输出与 Token

人与大语言模型交互时，通常看到的是完整的文字、代码或图片，但模型内部处理这些信息时，并不是简单地按照“一个汉字”或“一个英文单词”进行划分。文本首先会被转换为一系列更小的单位，这些单位通常称为 **Token**。

一个 Token 可能对应：

- 一个完整单词；
- 单词的一部分；
- 一个汉字或若干字符；
- 标点符号；
- 代码中的符号和关键字。

当我们向模型提供对话记录、大量源代码、多篇文档等内容时，这些内容会先被处理为一个个 Token，然后被送进模型的接口，模型生成的回答同样需要占用一定数量的 Token。

### 2.2 上下文与上下文窗口

**上下文（Context）**可以理解为模型在处理当前任务时能够参考的信息。它可能包括用户当前提出的问题，之前的对话内容，以及上传的文档等等。

同一个模型在不同上下文下得到的结果可能有很大差异。例如，当我们询问：*为什么这段电机通信程序偶尔会超时？* 如果只提供这一句话，模型能够利用的信息非常有限。但是如果同时提供电机通信方式、控制周期、相关代码以及超时时的日志，模型就能够在更完整的上下文中分析问题。

模型一次能够处理的上下文总量存在上限，这个范围称为 **上下文窗口（Context Window）**。在当下，大部分闭源与开源模型都支持较长的上下文窗口，而上下文管理已经成为 LLM 领域的一个重要课题。对于我们用户来说，需要理解两个问题：

第一，**上下文窗口大并不意味着可以无限加入信息。** 大量无关代码、重复日志和历史对话同样会增加模型处理任务的难度。真正应该提供的是 **与当前任务相关的信息**。<br>第二，**信息进入上下文以后，也不代表模型一定能够正确利用它。** 当上下文非常长时，模型仍然可能遗漏某些细节、错误理解文件之间的关系，或者受到无关信息干扰。

因此，在复杂项目中通常需要有意识地组织上下文，例如：先让 Agent 阅读项目结构，再确定相关模块，之后重点阅读少量关键文件，而不是没有选择地把整个仓库交给模型处理。

### 2.3 多模态输入

早期的大语言模型主要处理文本，而现代 AI 系统已经逐渐具备处理多种信息形式的能力。能够同时理解文字、图像、音频等不同类型输入的模型，通常称为 **多模态模型（Multimodal Model）**。

对于机器人开发来说，多模态能力非常实用。因为除了文字和代码，还经常需要处理程序报错截图，软件架构图，电路原理图，PCB 图片，甚至机器人机械结构照片等。这样往往比单纯用文字描述现象更加准确。

不过，需要区分三个不同层次：**模型本身是否具备某种能力、当前 AI 产品是否开放这种能力，以及具体工具是否能够访问相应的数据。**例如，一个模型可能具备图像理解能力，但某个 CLI 工具未必支持直接输入图片；一个 Coding Agent 可以读取本地源代码，也未必能够自动访问团队的在线文档。因此，在实际使用中不能只根据模型名称判断它能够完成哪些任务，还需要了解当前使用工具所提供的输入方式和权限。

### 2.4 信息范围对结果的影响

Token、上下文窗口和多模态能力最终都指向同一个问题：**模型只能根据当前能够获得的信息处理任务。**对于简单知识问题，模型自身已有的知识可能已经足够。但对于机器人项目中的工程任务，真正重要的信息往往存在于项目本身中，比如代码仓库，硬件接口文档，编译环境等等，这些内容不会因为模型能力很强就自动出现在它的上下文中。

因此，工程中使用 AI 时，需要 **先确认完成任务需要哪些信息，再确认这些信息是否已经进入模型能够使用的上下文。** 当仅靠当前上下文还不足以完成任务时，就需要让模型进一步读取文件、搜索资料、执行命令或调用其他工具。

## 3. 模型能力与外部工具

仅依靠模型本身，AI 能做的事情主要是基于已有上下文进行理解、推理和生成。它可以分析一段代码、解释报错、提出修改建议，但不会天然知道本地仓库中有哪些文件，也不能直接执行编译、读取最新网页或访问团队内部数据。要让 AI 真正参与工程任务，就需要把模型与外部工具连接起来。

### 3.1 模型生成与工具调用

最基本的交互方式，是模型根据当前上下文直接生成结果。例如，将一段 C++ 代码和编译错误交给模型，它可以根据已有信息分析可能原因，但此时它并没有真正执行程序，也无法确认项目中其他文件是否会影响结果。

如果 AI 系统能够使用文件系统、终端、浏览器、Git 或其他接口，它就可以进一步获取信息或执行操作。这类能力通常称为 **工具调用（Tool Use / Tool Calling）**。

以一个代码编译问题为例，带有工具能力的系统可以先读取 `CMakeLists.txt`、`package.xml` 和相关源码，再执行编译命令，根据真实错误继续搜索代码，必要时修改文件并重新编译。这里需要区分两个角色：**模型负责判断下一步应该做什么，工具负责真正获取信息或执行操作。**

因此，一个 AI 工具的实际能力并不只取决于底层模型。相同或接近的模型，如果一个只能进行文字对话，另一个能够访问代码仓库、Terminal 和 Git，它们处理真实工程任务的能力会有明显差异。

工具同时也意味着权限。读取文件、修改代码、执行 Shell、访问网络和操作 Git 的影响范围完全不同。对于工程开发，尤其是机器人项目，权限并不是越多越好，而应该与当前任务匹配。能够执行操作，只代表系统具备这种能力，并不意味着所有操作都应该自动执行。

### 3.2 检索与 RAG

当任务依赖大量外部资料时，把所有信息一次性塞进上下文通常并不合适。更常见的做法是先从资料中找到与当前问题相关的部分，再交给模型处理。这种思路通常称为 **检索增强生成（Retrieval-Augmented Generation，RAG）**。

例如，团队内部积累了大量开发文档。当成员询问某个通信超时问题时，系统可以先检索与电机通信、超时保护和底层控制有关的内容，再将相关段落加入上下文，而不是让模型一次读取整个文档库。关键词搜索、全文搜索、语义检索和向量检索都可以服务于同一个目标：**只把当前任务真正需要的信息送入模型上下文。**

代码 Agent 在大型仓库中的工作方式与此很接近。它通常不会从头到尾读取所有文件，而是先搜索符号、定位模块，再沿调用关系读取相关代码。对于使用者来说，重要的是理解这种“按需获取上下文”的工作方式，而不是提前研究检索系统的具体实现。3.2 检索与 RAG
